# ABI 12 六轴实物日志：两次广播后 READ 报错

[原始终端文本](dual-sync-fault5.txt)由操作者于 2026-10-09 提供；以下只解释日志可证明的内容。

| 证据 | 第一次同步写 | 第二次同步写 |
| --- | --- | --- |
| ABI、校准掩码 | 0x5254000c、0x3f | 同左 |
| WRITE | write_sent=1；广播没有 ACK | write_sent=1；广播没有 ACK |
| 发后故障 | fault=5，ID 5，phase=post_write_feedback，engine_fault=8 | fault=5，ID 2，同一阶段及底层码 |
| 成功的发后 READ | ID 1–4 | 仅 ID 1 |
| 未取得有效发后位置 | ID 5–6 | ID 2–6 |

RTL 的底层码 8 只在**应答包校验通过且舵机 ERROR 字节非零**时产生；这不是单纯超时。ABI 12 的六轴结果未保存该 ERROR 字节，因此不能从这份日志判定舵机报告的具体状态或物理原因。广播没有应答，不能把 write_sent=1 写成舵机 ACK。

第二条命令的现场起点相对第一条起点分别变化 +480、+352、-219、-479、+28、+453 count。这证明两次提交之间六轴位置读数均发生变化，符合操作者“六轴联动”的观察。第二条起点不是第一条运动的最终稳定落点；其中 ID 5 仅增加 28 count，不能据此宣称第一条六轴全部到位。第二条命令后也没有独立的六轴最终 READ。两条命令的 CLI 均报错，均不能计作“连续三轮六轴到位”的软件验收通过。

阶段管理按操作者要求将 G2 结束；G3 首要工作是只读记录六轴实际位置和原始舵机 ERROR 字节，识别并消除发后 READ 异常，再考虑静态抓放自动循环。不得依据这些起点自动回到旧 reference_count 端点。

随后操作者提供了[五轮静止诊断与越限拒绝](five-static-diagnoses-and-limit.txt)：六轴每轮 READ 均返回相同位置、ERROR=0；ID 2 目标 860 低于编入的下限 861，在提交前被 CLI 拒绝。这两项结果不解释运动时曾出现的 ERROR 非零。
