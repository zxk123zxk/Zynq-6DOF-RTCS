# 半自动闭环：`static capture` → 自动收坐标 → 抓取

**目标：在 PC 上打一句 `static capture`，上位机（Zynq 板）自己收下相机算出的毫米坐标，
稳定 0.5 s 后立刻跑已有的七步抓取，并把结果回给 PC。人不再抄两个数。**

2026-10-25 之前，坐标靠人眼从终端抄到板端（`--grasp-xy` 手输）。本方案把这一步自动化，
其余全部复用已验证的部件——**不新增任何运动逻辑**。

## 1. 三个部件

| 部件 | 跑在哪 | 职责 | 代码 |
| --- | --- | --- | --- |
| `capture_agent.py` | PC（带相机） | 采样 → 稳定判据 → 出点 → 发送 → 收结果 | `vision_v11/.../scripts/capture_agent.py` |
| `static_grasp_server.py` | Zynq 板 | 收一行 JSON → 校验 → 调状态机 → 回报 | `scripts/static_grasp_server.py` |
| `g3_station_runner.py` | Zynq 板 | 七步抓取（**未改动**） | `scripts/g3_station_runner.py` |

数据流：`相机 → YOLO → 单应→mm → 稳定 0.5 s → UDP/串口 → 板端 → PS 插值 → PL 时序 → 舵机`

## 2. 链路怎么选（先确认物理条件，再选传输）

### 2.0 先排除一条走不通的路：把相机接到板子上，让板子自己出坐标

2026-10-26 有人提议把 USB 相机插到 AX7Z020 的 USB 口，在板上跑 `camera_demo.py`，
让坐标"直接进 FPGA"。**结论：硬件上能接，但软件上跑不动，而且它并不"进 FPGA"。**

三条事实（都可复核）：

1. **USB0 挂在 PS 的 MIO 28..39 上**（`src/pl/vivado/ax7z020b_ps7_config.tcl`），
   所以摄像头接上去，数据进的是 **ARM 的内存**，**不是 PL 的逻辑**。
   要让画面进 PL，需要 V4L2 → DMA → VDMA → 自定义视频 IP 的完整通路；
   本仓库 RTL 里 `grep -i "vdma\|v4l2\|video"` 为空，即**不存在任何视频通路**。
2. **板端跑不了 YOLO**：XC7Z020 的 PS 是双核 Cortex-A9（32 位 ARMv7）。
   PyTorch 官方 wheel 只有 x86_64 / aarch64，**没有 armv7l** —— 不是"慢"，是装不上；
   `ultralytics` 也就无从谈起。
3. **速度差两个量级**：本机 CPU 实测 **0.25 s/帧**（imgsz 640）；A9 @667 MHz 上同类卷积网络
   通常慢 30–100 倍，即 8–25 s/帧。而 0.5 s 稳定窗至少要 3 帧，等于需要 **≈0.17 s/帧**。
   差距 50–150 倍。

**还有一条更根本的理由**：本作品的软硬件划分是"感知在上位机、时序在 PL"
（3.3 赛道看重软硬件划分依据）。把推理搬到板子的 ARM 上，会把这条分界线搅乱——
而且它本来也不是我们想论证的强项。

> 唯一技术上可能的变体：在板上用**非深度学习的轻量检测**（V4L2 取流 + HSV 阈值找白方块，
> C 或 numpy 实现，约 1–2 天）。它能跑，但鲁棒性远不如 YOLO（反光、遮挡、换件就崩），
> 而且仍然要自己解决"谁触发"。**不建议**，除非 11-04 之后要专门做一个"PL 视频通路"的加分项。

**所以链路绕不过去，而它很便宜**——见下文三档。

### 2.1 三档传输

| 拓扑 | 前置条件 | 板端命令 | PC 命令 |
| --- | --- | --- | --- |
| **UDP（首选）** | PC 与板在同一网段 | `--source udp --port 5005` | `--udp <板IP>:5005` |
| 串口 | PC 有 USB-TTL 且装着 pyserial | `--source stdin` | `--serial COM5` |
| 退化（现状） | 无 | 无 | 默认，只打印板端命令 |

**先查物理条件**，别猜：

```sh
# 板端
ip -4 addr show eth0          # 有 10.x/192.168.x 就是有网
ping -c3 <PC的IP>
```

> 2026-10-26 事实：本机（`zxkzxk`）只有 WiFi 10.83.133.202/15，没有物理网口。
> **但串口是通的**：`pyserial` 枚举到 **COM8 = Silicon Labs CP210x USB-to-UART**，
> 这就是 AX7Z020 的控制台，现在正插在这台机器上（`mode`/WMI 看不到它，只有 pyserial 能看到，
> 所以别用 `mode` 判断有没有串口）。pyserial 3.5 已装进 `D:\rtcs-venv`。
> **结论：串口档今天就能用，不需要买任何东西。**
> 另外 COM4/COM5 是 com0com 的虚拟串口对，只能用于离线自测，不能连板子。
> 要走 UDP 则需满足其一：① 板子 eth0 拿到 **10.83.x** 同网段地址；② 加 USB-以太网直连。

**30 秒探测（两侧各跑一次，就知道哪档能通）**：

```powershell
# PC：列出串口（有就说明串口档可用，记下 COMx）
.\env.cmd -c "import serial.tools.list_ports as p; print([x.device for x in p.comports()])"
```
```sh
# 板端：看 eth0 有没有 IP、能不能 ping 通 PC
ip -4 addr show eth0 | grep inet
ping -c 3 <PC的IP>
```

## 3. 协议（一行 JSON，UTF-8，换行结束）

```json
{"cmd":"static_capture","x_mm":333.42,"y_mm":36.08,"stable_s":0.72,"n":4,
 "spread_mm":[0.18,0.11],"conf":0.79,"conf_margin":0.36,"source":"capture_agent/udp"}
```

板端只认 `cmd="static_capture"`；其它行打印 `SERVER_IGNORE` 并丢弃——**不会被当作命令执行**。
坐标保留到 0.01 mm（满足"精确到 mm 的每一位"，且给后续误差分析留余量）。

回包（UDP 模式）：

```json
{"ok":true,"success":1,"grip":"contact","gripper_position":2408,
 "cycle_ms":7384,"arm_ms":7502,"fault":null,"x_mm":333.42,"y_mm":36.08}
```

## 4. 稳定判据（`--stable-s 0.5 --tol-mm 2.0`）

从最近 3 帧开始往前扩，取**最先**同时满足"x/y 极差 ≤ 2 mm"和"跨度 ≥ 0.5 s"的那一段，
坐标取该段中位数。抖动过的头部会被自然丢掉。

已单测（6 例全过）：

| 场景 | 期望 | 结果 |
| --- | --- | --- |
| 静止 5 帧跨 0.8 s | 判定稳定 | ✅ span 0.60 s，spread 0.10/0.10 |
| 静止 3 帧只跨 0.4 s | 不判定 | ✅ 0.5 s 门槛真的生效 |
| 静止 3 帧跨 0.50 s | 判定稳定 | ✅ |
| 抖动 5 mm | 不判定 | ✅ |
| 每帧移动 3 mm | 不判定 | ✅ |
| 先抖 3 mm 后稳定 0.7 s | 判定稳定，丢弃抖动段 | ✅ |

为什么需要它：单帧抖动 ±2~4 px ≈ 1~2 mm，刚放下的方块还会被手带得轻微晃动；
"稳定半秒"把这两类噪声挡在门外。

## 5. 全流程：冷启动 → 起服务 → 抓取 → 要回控制台

**唯一要理解的事：COM8（板子控制台）同一时刻只能被一方占用。**
所以流程就是"三次交接"——终端交出去、抓完再要回来。

| 阶段 | COM8 归谁 | 板端在做什么 | PC 在做什么 |
| --- | --- | --- | --- |
| ① 冷启动 / 拷载荷 | 终端程序 | shell | — |
| ② 起服务 | 终端程序（最后一刻） | server 前台占住 stdin | — |
| ③ 抓取 | **capture_agent** | server 等 stdin，收到就跑一轮 | 出点 → 写串口 → 收 REPLY |
| ④ 要回控制台 | 终端程序 | shell（server 已退出） | — |

### 5.1 冷启动 + 拷载荷（每次断电后都要做，`~/rtcs` 是 RAM）

```sh
# 板端串口：登录 petalinux（密码另输）→ 提权
sudo -i
ls /run/media/                                  # 确认挂载点，通常是 mmcblk0p1
SD=/run/media/mmcblk0p1
mkdir -p ~/rtcs/scripts ~/rtcs/config
cp -v "$SD"/*.py ~/rtcs/scripts/                # 5 个脚本，通配一次到位
cp -v "$SD"/*.toml "$SD"/*.json ~/rtcs/config/  # 4 个配置
cd ~/rtcs && chmod +x scripts/*.py && ls scripts config   # 应有 5 个 py + 4 个配置
head -8 config/grasp_teaching_table.json        # 确认是 6 点表（295..420）
```

- **`cp "$SD"/文件名` 中间不能有空格**：`cp "$SD" /g3_...py` 会被理解成"复制目录 + 复制到根目录"。
- 用通配 `"$SD"/*.py` 而不是逐个列名字：以后加脚本（比如今天的
  `static_grasp_server.py`）就不用再改这条命令。

### 5.2 起服务 = 把 COM8 交出去

```sh
cd ~/rtcs
sudo python3 scripts/static_grasp_server.py --source stdin
# 看到 SERVER_READY source=stdin 就对了；这时终端被它占住，打字不回显是正常的
```

然后**关掉 PC 上的终端程序**（MobaXterm / putty / 串口助手）。

> 关窗口不会杀掉板上的 server：这是串口控制台，不是 ssh 会话，没有 SIGHUP。
> 关的只是 PC 侧那个"读端"。

### 5.3 PC 出点并抓取

```bat
.\env.cmd scripts\capture_agent.py --serial COM8
rem 交互里输入：static capture
```

期望输出：

```
CAPTURE_START stable=0.50s tol=2.0mm timeout=6.0s
CAPTURE_SENT transport=serial COM8 115200 baud
BOARD_LOG 前 N 行板端输出：      <- 板端七步的 G3_STEP 行
CAPTURE_REPLY ok=True grip=contact cycle_ms=7900 grip_pos=2374 fault=None
CAPTURE_POINT x_mm=333.42 y_mm=36.08 stable=0.72s n=4 spread=0.18/0.11mm conf=0.79
```

### 5.4 把控制台要回来

重开终端程序 → 按 **Ctrl-C** → server 收到 SIGINT 退出 → shell 提示符回来。
（想再抓就回到 5.2；**不用重拷载荷**，除非断过电。）

**一次交接可以覆盖多轮**：agent 是交互式的，`static capture` 可以连着输 10 次，
中间不用重新开关终端——所以跑 10 次统计时只用交接两次（开头一次、收尾一次）。

### 5.5 两种模式

| 模式 | 板端命令 | 用途 |
| --- | --- | --- |
| dry-run | `--source stdin --dry-run` | 首连链路验证：七步只打印命令、不产生运动帧，`grip=dry_run` |
| 真跑 | `--source stdin` | 正常抓取，看 `grip=contact` / `empty` |

**UDP 档**（等板子 eth0 有同网段 IP 时再上：更快、不占控制台、可双向回包）：

```sh
sudo python3 scripts/static_grasp_server.py --source udp --port 5005 --dry-run
```
```bat
.\env.cmd scripts\capture_agent.py --udp <板IP>:5005
```

### 5.6 已知风险

- **DTR 复位**：CP210x 打开端口时可能拉 DTR。若一跑 agent 板子就重启，说明 DTR 接到了复位；
  换一路只接 TX/RX/GND 的 USB-TTL，或换不带 DTR 的桥接片。
- **只有一路 UART**：PS7 里只启用了 UART1（MIO48..49）作控制台，UART0 没使能，
  所以没法"控制台 + 数据"两路并行。要并行得改 `ax7z020b_ps7_config.tcl` 重新出比特流，
  11-04 之前不值得。

## 6. 排障

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `CAPTURE_FAIL stage=init 没有可用相机` | 预览窗口独占相机 | 关掉 `camera_demo*` 再跑 |
| `CAPTURE_FAIL reason=timeout` | 目标在动 / 框在跳 / 没放件 | 看它打的极差；静止后重试 |
| `CAPTURE_FAIL 板端 60s 内没有回包` | IP/端口错、防火墙、板端没在跑 | 先 `ping`，再确认 server 在跑 |
| 板端 `SERVER_IGNORE 不是 JSON` | 串口回显/提示符混进了行 | 正常现象，server 会取 `{`…`}` 之间的内容 |
| `grip=empty` | 夹爪合到底没夹到东西 | 看 `x_mm/y_mm` 是否越界或 y 偏离 36 |
| 板端起不来 | `~/rtcs` 是 RAM，断电丢了 | 从 SD 重拷（含新增的 `static_grasp_server.py`） |

## 7. 分工合规（这条要写进报告）

- **感知与抓取点决策在上位机**：YOLO 推理、单应变换、稳定判据都在 `capture_agent.py`。
- **实时执行在 PS/PL**：坐标 → 六轴目标（PS 插值）→ PL 组帧/限位/时序 → 舵机。
- 板端 `static_grasp_server.py` **只做"收指令 + 调状态机"**，不碰相机、不做推理。
  所以这条链路没有把"策略"塞进 FPGA，符合赛道红线；FPGA 的价值另见
  [FPGA 在项目中的作用与赛道符合性](10-FPGA在项目中的作用与赛道符合性.md)。
