## 1. 白纸包裹：有效，但有两个副作用（新绿带 run 1169 帧，已抽帧取证）

**结论：白纸包裹有效，你的判断可复现。** 取证帧见
[artifacts/reports/vision-diagnosis-20261014/](../../artifacts/reports/vision-diagnosis-20261014/)：

| 证据帧 | 客观结果 |
| --- | --- |
| [帧 0010](../../artifacts/reports/vision-diagnosis-20261014/绿带-白纸包裹被检出cube0.75-帧0010.png) | 深绿带上的白纸包裹物体被检出 **`cube` conf=0.75** —— 对比度问题确实解决了 |
| [帧 0850](../../artifacts/reports/vision-diagnosis-20261014/绿带-俯拍白纸物体conf0.82但背景多处误检-帧0850.png) | **俯拍**时带面白物体 **conf=0.82**，最好的一档；但同帧还有 4+ 个背景误检框 |
| [帧 1150](../../artifacts/reports/vision-diagnosis-20261014/绿带-同一白物体被判cylinder0.69类别不稳定-帧1150.png) | **同一个白物体这次被判 `cylinder` conf=0.69** —— 类别不稳定 |

**副作用 1：类别不稳定。** 同一个白物体，帧 0850 判 `cube`、帧 1150 判 `cylinder`。
若抓取策略按类别分叉（方块抓法 ≠ 圆柱抓法），就会抓错。
→ **竞赛轨建议：不区分类别**，取置信度最高的一个检测当"目标物"即可。
这样直接绕过类别混淆，**不需要重训模型**。

**副作用 2：高悬俯拍把背景杂物一起收进来了。** 逐百帧统计（`detections.jsonl`）：

| 帧段 | 平均检出数 | 最高置信度均值 | 备注 |
| --- | --- | --- | --- |
| 0–99 | 1.97 | 0.562 | 近景，只有带面 |
| 400–499 | **0.57** | 0.157 | 最干净的一段 |
| 800–899 | 5.91 | 0.714 | 俯拍后：桌面、地板、人、可乐罐全入画 |
| 1100–1168 | **7.13** | 0.832 | 检出多但**大半是背景** |

帧 0850 里被判 `cylinder` 的红罐是**真物体**（不是误检），旁边的木纹、地板、人腿才是误检。

> **这直接推翻"ROI 可省"的想法**：高悬俯拍必然把工作区之外的杂物收进画面，
> 不限 ROI 时误检会成倍上升。ROI 在这里不是"滤噪声的补丁"，是**让画面回到工作区**的唯一手段。
> 另一条同向证据：俯拍后白物体在画面里变得很小 → **像素尺度下降**，
> 用 `plane_mapping calibrate` 的 `pixel scale` 行可以量化（见决策文档 §6.3）。

**顺带修正一处证据路径**：该 run 的 `summary.json` 里
`output = D:\GitProjects\Zynq-6DOF-RTCS\outputs\vision\live_test_120`，
与当前工作区不同目录。**归档时以 `summary.json` 的 `output` 字段为准**，
并注明"素材来自另一工作副本"，避免以后对不上。

## 2. 竞赛轨口径：我把这些砍掉了

你批评"保守测试太多"，这个批评部分成立。按仓库既有的[双轨制](../0.1hardware_bringup.md)
（竞赛轨只保留红线门禁，流程门禁属归档轨），我把之前的建议**降级/砍掉**如下：

| 之前的建议 | 现在的口径 |
| --- | --- |
| `--max-export 300` + **逐帧人工裁定表** | **降级为归档轨**。竞赛轨只留 `vision_runs/<run>` 原始产物 + 2–3 张代表帧；裁定表周末需要写文档时再补 |
| 先花 1 小时比 `--mode opencv` | **砍掉**（你已决定继续用 YOLO，且 YOLO 权重就是垂直俯视数据训的） |
| 补光作为方案 | **砍掉**（比赛现场不可能打探照灯）。但"对比度不足"这个根因判断保留，白纸包裹就是它的解法 |
| 平面映射 ≥6 点 + ≥3 独立验证点 + mean/RMS/max 报告 | **保留求解 ≥6 点**，验证点**降到 1–2 个**够用；不需要误差报告，看一个数就行 |

**仍然保留（因为便宜且防不可逆事故，不是流程仪式）**：
- 红线门禁本身（独立供电 / 物理禁发 / 独立急停）——这是你自己的约定；
- 映射**凸包外拒绝**、置信度不足**放弃本次抓取**——三行代码，省掉"机械臂对着空气乱抓"；
- 平面映射**必须做**（否则像素无法变成毫米，抓取无从谈起），但它是**1 天**的事，不是一周。

**另外提醒一句进度**：今天机械臂侧的进展是"只读基线 + ID 5 区间"两项**已归档**；
视觉侧虽然讨论很多，但**真正没动的是 G3 的六工位示教与单循环**。
瓶颈不在测试仪式，在 G3——明天优先它不是保守，是主线。

## 3. 可借鉴的实现（GitHub / CSDN）

按"能不能直接抄到我们的链路上"排序。**注意：全部是 PC + Python + OpenCV 的 eye-to-hand 平面映射路线，与我们完全同构。**

| 资源 | 里面有什么可直接用 | 注意 |
| --- | --- | --- |
| [kaixindelele/**Eye-to-Hand-Calibration**](https://github.com/kaixindelele/Eye-to-Hand-Calibration) ⭐首推 | **中文、场景完全一致**：相机固定 + 末端在固定平面移动，只求单应矩阵。`calibration_class.py` 可独立使用，含**重投影误差 avg_e** | 它用机械臂末端针尖取标定点；我们的 `plane_mapping` 已覆盖同一思路，可对照它的误差口径 |
| [RawichSinghachai/**me484**（SCARA Robot）](https://github.com/RawichSinghachai/me484) | `calibration.py` 像素→真实坐标；`vision.py` 颜色检测；`servo.py` + `set_zero.py` 舵机零位 | 树莓派 + PCA9685 舵机，**舵机零位/标定流程可借鉴**；它做的是颜色检测 |
| [Martin-Ansteensen/**steppper-robot-arm**](https://github.com/Martin-Ansteensen/steppper-robot-arm) | **6-DOF 抓取整机参考**：UI 里选 4 点圈工作区 → **去畸变(deskew)** → 两点标定 → 像素映射到机械臂 XY；含**正逆运动学**与抓放 demo | 它是步进电机 + Arduino；**"选 4 点圈区域"正好是我们要的 ROI**，姿态/IK 可参考 |
| [Hiwonder/**ArmPi-FPV**](https://github.com/Hiwonder/ArmPi-FPV) | **和你的硬件同一家（幻尔）**：总线舵机驱动 `hiwonder_servo_driver`、颜色标定 `lab_config`、抓取应用 `object_picking` | 依赖 ROS/MoveIt，**不要全搬**；但**总线舵机的 ID/角度映射代码可以直接对照** |
| [xsatvik/**lerobot**（fork）](https://github.com/xsatvik/lerobot) | `HAND_EYE_CALIBRATION_GUIDE.md`、`camera_calibration_files/`（ArUco 采集/求解/校验）、`pick_at_xyz.py`、`goto_xyz.py` | 面向 SO-100 + ROS2；有 **ArUco 标定**流程（我们已弃用棋盘格，但它的**校验与精修脚本**思路可看） |
| CSDN 摘要型文章（无需跑代码，看结论） | 九点标定完整代码（`findHomography` + 齐次归一化）、**"抓取点取检测框底边中点而非中心"**、实测误差 3–8 mm 属正常 | 齐次归一化忘了除第三项是**最常见的 bug**；我们的 `plane_mapping` 已处理 |

**三条从这些案例里得到的最有价值的具体结论**（都和我们已有实现一致或可立刻吸收）：
1. **固定相机 + 平面抓取的行业标准做法就是九点单应**，不做内参、不做畸变——**我们的路线是对的**，不是"偷懒"。案例里的实测误差也是 3–8 mm 量级。
2. **抓取点用检测框底边中点，而不是框中心**——因为夹爪的接触点在地面的投影更接近底边。**这一条我们还没做，值得加进 G4 步骤 5。**
3. **"先选 4 点圈出工作区"是所有同类项目的共同做法**（steppper-robot-arm 的 UI 就是这么干的）——再次说明 ROI 是标准件，不是我的发明。
