# G3 状态机编排层 · 骨架与验收（2026-10-16）

等待相机/训练的空窗期产物：把"单循环六步"做成**参数化状态机**，一份代码同时服务
盲抓（固定示教点）和视觉抓（映射坐标）。全程不碰真舵机，离线可回归。

## 1. 新增文件与原理

| 文件 | 职责 | 原理 |
| --- | --- | --- |
| `scripts/g3_station_runner.py` | **状态机编排层（核心）** | 读已确认的 `g3_station_plan.json` → 复用 `g3_offline_plan.validate` 门禁（ID5 放行/越界/preflight/六步顺序）→ 顺序执行六步：每步 subprocess 调 `rtcs-pl-g2-six move-six`（真正的组帧/限位/总线时序在 PL）→ 解析 `RTCS_PL_G2_SIX_OK` / `ERR g2_six_fault` 判定成败 → **故障留痕不锁死**（某步失败→记故障→跳 exit 安全回位→本轮失败→下一轮继续）→ 支持 `--once` / `--loop N` / `--dry-run` / `--grasp-xy` |
| `scripts/grasp_point_map.py` | **抓取点参数化几何层** | 工作平面 `(x,y)` → 六轴 target。示教表最近邻/双线性插值（ID 1-3 随坐标变、ID 4-6 固定姿态）；`map_grasp_analytic` 精确两连杆解留 TODO 待工位几何实测 |
| `sim/run_g3_station_runner_guard.sh` | **离线回归** | mock 的 move-six（Python 脚本），测四件事：①六步顺序 ②故障不锁死（grasp 失败→exit 回位→第二轮跑通）③越界计划被拒 ④`--grasp-xy` 覆盖抓取点 |

## 2. 数据流

```
visual (u,v) ─plane_mapping.py─> (x,y)
                                    │
grasp_point_map.map_grasp(x,y,table,fixed_pose) ──> 六轴 target（覆盖 approach/grasp/lift 的 ID1-3）
                                    │
g3_station_runner.py ──> 每步 move-six ──> rtcs-pl-g2-six ──> PL（组帧/限位/总线）
      │（盲抓时跳过映射，直接用计划里的固定示教点）
      └─ 六步：standby → approach → grasp → lift → place → exit
```

## 6. 安全边界（与现有红线一致）

- 编排层**不发任何一帧**，只调 `rtcs-pl-g2-six`（帧由 PL 拼、限位由 PL 裁）；
- 越界/未放行 ID5/缺 preflight 的计划在 `validate` 阶段即被拒，不会执行任何运动；
- exit 步回位失败 → 立即终止（安全无法保证时不硬继续）；
- 单步故障如实留痕、不锁死后续轮次，但**不自动重试**同一命令。

## 7. 夹爪拆分（2026-10-19 修订，必读）

### 7.1 为什么不能把夹爪并进 move-six

`move-six` 的到位判定是**六轴连续三轮全部进容差带**（默认容差 30 count）。
夹爪夹住物块的物理结果是：舵机被物块顶住，停在接触位置（10-17 实测命令 2200 → 停 2367），
同时舵机 ERROR 报过载（`servo_error_raw=0x20`）→ PL 判 `fault=5`。
所以只要把 ID 6 的闭合目标写进 `move-six`，**每一次抓取都会被判失败**，而且这个结论与机械是否正常工作无关。

### 7.2 现在的动作拆分

一个抓取动作拆成两段，走两条不同的 CLI：

```
六轴到位（夹爪保持张开 2500）  →  rtcs-pl-g2-six move-six
        ↓
夹爪闭合（单轴，允许过载）      →  rtcs-pl-g2 move --id 6 --target 2200
        ↓ 判定 CONTACT，取回接触位置（如 2367）
后续各步 ID 6 目标 = 接触位置   （Hold，容差放宽到 100）
        ↓
夹爪张开（单轴）                →  rtcs-pl-g2 move --id 6 --target 2500 → 解除 Hold
```

判定口径（`judge_gripper`）：

| 输出 | 语义 | 是否算成功 |
| --- | --- | --- |
| `RTCS_PL_G2_OK` | 正常到位 | 是 |
| `write_sent=1` 且 `servo_error_raw` 带 `0x20` 过载位（闭合步 `expect_overload=true`） | `CONTACT` 夹住了 | 是，单独留痕 |
| 其余（含 `write_sent=0`） | 真故障 | 否 |

**注意**：过载只在"闭合"这一步被接受，且要求计划里显式写了 `expect_overload: true`；
张开步期望 `false`，张开失败（如 10-17 的 `fault=8`）仍然算失败，不会静默通过。

### 7.3 计划里的写法

`config/g3_station_plan.json` 的两步增加可选字段 `gripper`：

```json
{"name": "grasp", "target_count": [2061, 2130, 2073, 3009, 2006, 2500],
 "gripper": {"command": "close", "target_count": 2200, "expect_overload": true}}

{"name": "place", "target_count": [1164, 2433, 2030, 2723, 2013, 2500],
 "gripper": {"command": "open", "target_count": 2500, "expect_overload": false}}
```

要点：**grasp 步 `target_count` 的 ID 6 必须是"张开"值（2500）**，闭合目标只放在
`gripper.target_count`。place 步的 ID 6 同理只是名义值，执行时会被 Hold 覆盖，
到位后才张开。`gripper.target_count` 必须落在 ID 6 实测范围 2050–3000 内，门禁会拦。

### 7.4 新增命令行参数

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `--single-cli` | `rtcs-pl-g2` | 夹爪单轴 move 可执行路径（回归注入 mock） |
| `--observe-ms` | `8000` | 六轴到位观察期；长杆大位移（ID2 +1241）默认 5000 不够，会 fault=9 |

### 7.5 占位步门禁（新增）

`--dry-run` 允许打印含占位步的计划（便于人工审阅指令）；
**真跑**（不带 `--dry-run`）时，任何一步 `measured_at` 以 `TODO` 开头即拒绝整份计划：

```
G3_PLAN_REJECTED approach: placeholder pose; teach this station point before executing
```

这条门禁把"用复位值占位当 approach/lift 真跑"这类事故挡在发帧之前。

## 8. 限位表与 PL 综合常量的同步校验（2026-10-19 新增）

`scripts/check_limit_sync.py`：把 `config/g2_measured_limits.toml` 与
`src/pl/rtl/g2_board_limits_pkg.sv` 的 `SAFE_MIN/SAFE_MAX/SPEED_MAX_RAW/CALIBRATED_MASK`
逐轴对比（注意 SV 打包字面量是高位在前，脚本按"读入后反转"还原成 ID 1..6）。

- 已挂进 `sim/run_regression_wsl.sh` 的**第一项**，输出 `LIMIT_SYNC_OK`；
- 不同步时直接失败并逐条列出 `LIMIT_SYNC_MISMATCH ID n safe_max: toml=2500 pl=1500`；
- 起因：10-17 示教后只改了 toml，pkg 仍是 10-13 值，板端 `move-six` 在 CHECK_GUARD
  阶段以 `fault=12 measured_limit_rejected / write_sent=0` 拒发。**改限位 = 必须重综合 bitstream**。

### 8.1 限位有两处副本，生产板用的是包装层那份（10-19 补）

| 位置 | 谁在用 | 形式 |
| --- | --- | --- |
| `src/pl/rtl/g2_board_limits_pkg.sv` | 非 TTL 变体（`rtcs_axi_wrapper_bd` 用 `rtcs_top` 默认参数） | SystemVerilog 包 |
| `src/pl/rtl/rtcs_axi_wrapper_ttl_bd.v` | **生产板（带舵机 IO 的 TTL 变体）** | Verilog 字面量 |

BD 的 module reference 顶层必须是 Verilog(.v)，而 Verilog 不能引用 SystemVerilog 包常量，
所以 TTL 包装层只能复制一份字面量。**两处都要改，脚本两处都校验**（输出里 `sources=` 会列出
被校验的包装层文件名）。

10-17 的坑比原先判断的更靠前一层：pkg 当时已改（ID2 2500/ID4 3100），但 TTL 包装层仍是
1500/2861 —— 哪怕当时重综合了，产出的 bitstream 也还是旧限位。

### 8.2 必须用 `ttl` 变体综合

```
powershell -ExecutionPolicy Bypass -File scripts/build_vivado.ps1 -Build -Ttl
```

只带 `-Build` 生成的是**不导出舵机 IO** 的变体（XSA 约 377 KB，正常约 645 KB）：
上板后 `limits` 全为 0、`move-six` 直接 `six_axis_uncalibrated`。
判据：综合日志出现 `RTCS_G1_TTL_IO_OK tx=U20 rx=V15 inhibit=W15 pullup=TRUE`。

## 9. 实测路径点（2026-10-20 全流程手动跑通）

10-20 手工走通了「抓取 → 上抬 → 放置 → 回抬高位 → 抓取准备位」的完整闭环，逐步 `diagnose` 记录如下。
计划 `config/g3_station_plan.json` 已按这组值填实。

| 阶段 | ID1 | ID2 | ID3 | ID4 | ID5 | ID6 | 说明 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 默认/停机位 | 2003 | 884 | 2984 | 2859 | 2004 | 2063 | 开机与收工位置，不在循环内 |
| 1.1 抓取准备 | 2041 | 2018 | 2230 | 2789 | 2009 | 2619 | = standby / approach / grasp 的六轴目标（夹爪张开） |
| 1.2 闭合 | — | — | — | — | — | 2411 | 单轴闭合，实测停在 2411，**无过载** |
| 2 抓取上抬 | 2045 | 1240 | 2534 | 3120→**3100** | 2005 | 2404 | = lift 位；ID4 实测 3120 超 PL 上限，按 3100 下发 |
| 3.1 放置位 | 2875 | 2140 | 2335 | 2709 | 2005 | 2409 | = place 位 |
| 3.2 张开 | — | — | — | — | — | 2759 | 张开目标 2760，实测 2759 |
| 3.3 退让抬升 | 2875 | 1240 | 2534 | 3100 | 2005 | 2760 | = retreat 位：**原地上抬、ID1 不动**，避免张爪后横移刮倒已放下的小方块 |

| 5 回到抓取准备 | 2041 | 2018 | 2230 | 2789 | 2009 | 2619 | 下一轮 standby 从抬高位下降到这里 |

对应**七步**：

```
standby  = 抓取准备位      [2041, 2018, 2230, 2789, 2009, 2619]
approach = 抓取准备位
grasp    = 抓取准备位 + 闭合 2400
lift     = 抓取上抬位      [2045, 1240, 2534, 3100, 2005, 2404]
place    = 放置位          [2875, 2140, 2335, 2709, 2005, 2409] + 张开 2760
retreat  = 放置侧退让抬升  [2875, 1240, 2534, 3100, 2005, 2760]
exit     = 抬高位回抓取侧  [2045, 1240, 2534, 3100, 2005, 2619]
```

> **retreat 为什么单列一步（10-20 晚新增）**：原来 place 张开后直接 `exit`，`exit` 的 ID1 要从 2875
> 转到 2045，而此时爪还在放置高度，横移会扫到刚放下的小方块。新增 `retreat` 先**只抬 ID2/ID3/ID4
> 到抬升角度、ID1 原地不动**，爪离件后再转基座。`retreat` 的 ID2/3/4 直接复用已实测的 `lift`
> 抬升角度，ID1 保持放置侧 2875——这个组合是**推导值**，首次跑请目视确认不擦碰；
> 若 ID2 到不了 1240，改成 1400 再试。
>
> 同时修正 `exit` 的 ID6：原来是 2404（照抄 lift 的接触位），会**把已张开的爪子重新合拢**；
> 现在固定为张开值 2619。

**与 10-19 的差别**：不再追求"ID2 ≤ 2000"，而是用**抬高位（ID2=1240）**把跨区路径抬起来，
两区之间靠抬高位中转。10-19 的门禁已降级为告警，不再拦截。

**夹持段一律走六轴（2026-10-20 晚，PL 掩码方案）**：

之前"夹紧→过载→move-six 判死→只能逐轴"的两难，已由 PL 的**逐轴忽略掩码**根治：

| 寄存器 | 地址 | 含义 |
| --- | --- | --- |
| `REG_G2_SIX_IGNORE` | `0x11C`（只写） | `[5:0]` 错误掩码：屏蔽该轴回包的舵机 ERROR（仅 `engine_fault==8`，传输层故障照报）；`[11:6]` 到位掩码：该轴不参与"三轮全轴进带"判定 |

CLI 对应两个参数（只对 `move-six` 有效）：`--ignore-error ID`、`--ignore-arrival ID`。

编排层固定这样下发：

- **每条** `move-six` 都带 `--ignore-error 6`——夹爪夹紧必然过载，但不再拖死六轴命令；
- 除 `grasp` 外都带 `--ignore-arrival 3`——ID3 只在抓取那一步要求精确，搬运途中大致到位即可；
- **夹持期间（`lift` / `place`）额外带 `--ignore-arrival 6`**——见下；
- 仍带 `--tolerance 3:100`（ID3 实测会差 60 左右）。

> **为什么还要放行 ID6 的到位判定（10-20 晚补）**：实抓时 ID6 顶着物块，位置会在过载保护的
> "一收一顶"之间来回漂，实测漂移常超 100 count。它的目标已被接触位置钉死，不需要参与"连续三轮
> 进带"，但之前仍参与判定，于是整条命令**空等满 8 秒观察期**——表现为"空抓时迅速上抬、实抓时愣半天"。
> 加上 `--ignore-arrival 6` 后实抓与空抓的抬升响应一致。

**速度分级（10-20 晚，`speed_raw` 原为 500）**：

| 段 | `speed_raw` | 理由 |
| --- | --- | --- |
| standby / approach / grasp | 1000 | 近件定位，留精度余量 |
| lift / place（带载） | 1200 | 带物块，太快会甩动 |
| retreat / exit（空载） | 1400 | 纯空程，接近 PL 上限 1500 |
| 夹爪闭合 / 张开 | 800 / 900 | 原 500 太慢，冲击仍可控 |

> 加速的代价是到位后可能过冲震荡；PL 的"连续三轮进带"会自动多等一轮，不会误判。
> 首轮跑请留意 `elapsed_ms` 是否下降、以及有没有新出现的 `fault=9`。

> 掩码按命令模式生效：`move-six`(mode 1) 用错误掩码与到位掩码；`calibrate-step`(mode 2) 不套用；
> `stop`(mode 3) 忽略舵机 ERROR（急停必须能保持，不能因为夹爪过载而失败）。

`--transit per-axis` 仍保留，但只作排障用，正常不再需要。

### 9.2 运行

```sh
# 先 dry-run 审阅七步命令（应看到 --ignore-error 6、--ignore-arrival 3，lift/place 另有 --ignore-arrival 6）
sudo python3 scripts/g3_station_runner.py config/g3_station_plan.json --once --dry-run

# 机构复位到默认位（可选，建议每次开跑前）
sudo rtcs-pl-g2-six --uio /dev/uio0 move-six \
  --axis 1:2003:500:10 --axis 2:884:500:10 --axis 3:2984:500:10 \
  --axis 4:2859:500:10 --axis 5:2004:500:10 --axis 6:2063:500:10 \
  --observe-ms 8000 --execute

# 跑一轮 / 连续 3 轮 / 连续 10 轮
sudo python3 scripts/g3_station_runner.py config/g3_station_plan.json --uio /dev/uio0 --once
sudo python3 scripts/g3_station_runner.py config/g3_station_plan.json --uio /dev/uio0 --loop 3
sudo python3 scripts/g3_station_runner.py config/g3_station_plan.json --uio /dev/uio0 --loop 10
```

**每步都会打印 `elapsed_ms`**（10-20 晚新增），专门用来定位"哪一步慢"：

```
G3_STEP name=standby result=OK elapsed_ms=1834
G3_STEP name=grasp.gripper result=CONTACT elapsed_ms=1203 position=2411
G3_STEP name=lift result=OK elapsed_ms=2650 gripper_hold=2411
G3_CYCLE timing elapsed_ms=10643
```

判读：

- `grasp.gripper result=OK` / `result=CONTACT` 都算夹住——前者没过载，后者过载但已被掩码屏蔽，
  后续六轴照常；
- **某步 `elapsed_ms` 接近 8000 + 上一步耗时 → 那一步在等满观察期**，说明有轴没进带（对 ID6 就该
  带 `--ignore-arrival 6`，对其他轴则要 `diagnose` 看实际停点）；
- `fault=9 fault_id=n` → 该轴没到位。先 `diagnose` 看实际停在多少，再决定改计划值或加中间位；
- 若出现 `fault=5` 且 `engine_fault` 是 3..7（不是 8），那是**传输层**故障（接线/共地/波特率），
  掩码不覆盖，必须查硬件；
- 急停：`sudo rtcs-pl-g2-six --uio /dev/uio0 stop --execute`。

> `--transit per-axis` 仍保留（逐轴 ID3→ID2→ID1→ID4→ID5），但正常不再需要，只在某根轴于
> 六轴联动中被压进死区时临时排障用。

### 9.3 视觉抓取（2026-10-21 新增）

视觉给的是**传送带平面毫米坐标**（`center_x_mm/center_y_mm`），要变成六轴目标还差一层：
`mm → ID1-3`。这一层用**示教点表插值**，不写 IK。

**三个环节，两个新脚本**：

| 环节 | 在哪 | 命令 |
| --- | --- | --- |
| ① 取点 | PC（队友的 `.venv`） | `scripts/grasp_point.py` |
| ② 建表 | 板端 | `scripts/teach_add_point.py` |
| ③ 执行 | 板端 | `g3_station_runner.py --grasp-xy … --teaching-table …` |

**① PC 取点**（多帧取中位数，压掉单帧抖动）：

```powershell
cd vision_v11\Zynq_RTCS_YOLO_Vision_Module_v1_1
.\.venv\Scripts\python.exe scripts\grasp_point.py --frames 5
```

输出：

```
GRASP_POINT x_mm=243.7 y_mm=38.2 class=Cube conf=0.86 frames=5/5 x_spread=1.2mm
# 板端执行（复制这一行）：
sudo python3 scripts/g3_station_runner.py config/g3_station_plan.json --uio /dev/uio0 \
  --grasp-xy 243.7,38.2 --teaching-table config/grasp_teaching_table.json --once --dry-run
```

`x_spread` 是这几帧 x 的极差：**>3 mm 说明框在跳**（光照/运动模糊/遮挡），
先把工况稳定下来再抓，别急着调机械臂。

**② 板端建表**（每点一次；臂摆到该点、夹爪正好包住物块时执行）：

```sh
sudo python3 scripts/teach_add_point.py --x-mm 60  --y-mm 40
sudo python3 scripts/teach_add_point.py --x-mm 240 --y-mm 40
sudo python3 scripts/teach_add_point.py --x-mm 420 --y-mm 40
```

- 脚本读 `diagnose` 取 ID1-3，**不发任何运动帧**；
- 会比对 ID4-6 与 `grasp` 步的固定姿态，偏差 >30 就告警——**姿态不一致的点插值出来没有意义**；
- 自动排序、同坐标覆盖、少于 3 点提示退化为最近邻。

**③ 执行**：

```sh
# 先 dry-run 看 ID1-3 有没有被换成插值结果（place/retreat/exit 不应变化）
sudo python3 scripts/g3_station_runner.py config/g3_station_plan.json --uio /dev/uio0 \
    --grasp-xy 243.7,38.2 --teaching-table config/grasp_teaching_table.json --once --dry-run

# 真跑
sudo python3 scripts/g3_station_runner.py config/g3_station_plan.json --uio /dev/uio0 \
    --grasp-xy 243.7,38.2 --teaching-table config/grasp_teaching_table.json --once
```

**五条纪律**：

1. **坐标系必须同一套**：示教点的 `(x_mm, y_mm)` 与 `calibration.json` 同为
   「原点=传送带左下角、+x 沿带长、+y 沿带宽」。写错方向 = 整体偏转，且看起来像机械误差。
2. **只在 ID4-6 与 grasp 步一致时录点**，否则插值出来的 ID1-3 与固定姿态不匹配。
3. **点数 <4 就退化为最近邻**，等于三个离散档位。要连续覆盖就得 ≥5 点；3 点只能抓点附近。
4. **越出示教区间只告警不阻断**（`G3_WARN grasp-xy x=… outside taught range`）。外推精度没有
   保证，现场偶尔够一下可以，但录数据时不要把外推点算作达标。
5. **`lift` 用固定的标准抬升位**（10-21 定）：`--grasp-xy` 只覆盖 `approach` / `grasp`，
   `lift` **保持计划里的 `[2045,1240,2534,3100,2005]`** —— 那是 10-20 跑 `--loop 3` 全绿
   验证过的姿态，是唯一确定不撞底座/传送带的抬升位。
   若某个点确实需要不同抬升高度，再用 `--lift` 逐点录 `lift_targets` 覆盖（可选）。

> **为什么不能用固定增量**：抬升量与关节增量的关系取决于基座角。原始位点
> `[2041,2018,2230]` → `[2045,1240,2534]` 的增量是 `[+4,-778,+304]`，但视觉抓取位
> 基座在 1704（偏了 337 count）时，同样的增量会让末端过度伸展、**撞到底座**
> （10-21 实测 `fault=9 fault_id=4`）。所以每个点都要把"抬起来的样子"实测一次。
>
> **录抬升姿态**（夹住物块、抬起一定高度、确认不碰周围之后）：
>
> ```sh
> sudo python3 scripts/teach_add_point.py --x-mm 318.6 --y-mm 74.8 --lift
> ```
>
> 输出 `TEACH_LIFT {"x_mm":…,"targets":[…],"lift_targets":[…]}  TEACH_LIFT_OK`。
> 该点必须先用不带 `--lift` 的方式录过抓取姿态，否则报 `LIFT_NEEDS_POINT`。
> 重录抓取姿态时会**保留**已录的 `lift_targets`，不会覆盖。

> **这个坑踩了两次，最后的结论很简单：抬升就回到那个验证过的固定位。**
>
> ① 最早把 `lift` 也算进"随平面坐标变化的步"，插值把 ID1-3 写成和 grasp 一样，
> **抬升动作直接消失** —— 原地转手腕就带着物块横移，扫到传送带。
>
> ② 改成"抓取位 + 固定关节增量"推导后，在基座偏移 337 count 的点位上末端过度伸展、
> **撞到底座**（`fault=9 fault_id=4`）。
>
> ③ 最终做法：**不推导**，`lift` 就是计划里那个固定抬升位。理由很朴素——它是唯一被
> `--loop 3` 全绿验证过的抬升姿态，终点确定安全；而推导出来的终点从没被验证过。
>
> 运行时看这一行确认是固定位而非推导：
>
> ```text
> G3_INFO grasp_xyz=[1704, 1779, 2440] lift_xyz=[2045, 1240, 2534] | lift source: plan default verified pose (not derived)
> ```
>
> **注意**：固定抬升位保证的是**终点安全**，不保证**从任意抓取位到它的中间路径**。首次在
> 新位置抓取时仍要目视确认。另：限位只防舵机超程、**不防自碰撞**——ID2 在 861 下限之上也照撞。
