本文回答四件事：**识别指令怎么跑**、**像素怎么变成运动指令**、**怎么保证这一跳不错**、
**每个人的活怎么排**。ROS2 的取舍见 §7。

## 1. 环境（本机已修好，两个坑都填了）

### 坑一：venv 不能跨机器搬

原 `.venv` 是队友在另一台电脑上创建的，`pyvenv.cfg` 里 `home = H:\Miniconda`，所以
`.venv\Scripts\python.exe` 一启动就报 `No Python at 'H:\Miniconda\python.exe'`。
而且那个 venv 里**只装了 pip 和 setuptools，没有 torch、没有 ultralytics**——所以
`camera_demo.py` 在本机从来没真正跑起来过。

> **venv 不能跨机器搬**，这是 Python 的机制，不是队友写错了代码。
> 以后只交换 **源码 + `requirements.txt` + `models/best.pt`**，不交换 `.venv`。

### 坑二：项目路径太深，撞 Windows 260 字符上限

在项目内重建 venv 后装 torch 会失败：

```
OSError: [Errno 2] No such file or directory:
  ...\.venv\Lib\site-packages\torch\include\ATen\ops\
  _scaled_dot_product_fused_attention_overrideable_backward_compositeexplicitautograd_dispatch.h
```

这条路径**正好 260 字符**，就是 Windows 的 `MAX_PATH` 上限。

**解决**：venv 建在短路径，不动系统注册表。

```bat
python -m venv D:\rtcs-venv
D:\rtcs-venv\Scripts\python.exe -m pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

版本必须 **Python 3.12**（`torch==2.5.1` 的 wheel 只覆盖 3.9–3.12，**3.13 装不上**）。

### 统一入口 `env.cmd`

模块根目录新增 `env.cmd`，它指向 `D:\rtcs-venv`，团队所有人都用这一条：

```bat
.\env.cmd scripts\camera_demo.py --check-model
.\env.cmd scripts\camera_demo.py --camera-index 1 --backend dshow
.\env.cmd scripts\grasp_point.py --frames 9 --trial 1
```

**相机固定 index=1 / dshow**（`grasp_point.py` 的默认值）。index 0 是另一个镜头、对着天花板，
读数会跑到 200/200 那种明显不可能的值——用错了就换 `--camera-index 0` 明说。

已实测通过：`torch 2.5.1+cpu / cv2 4.10.0 / ultralytics 8.4.43`，`best.pt` 加载正常（设备 cpu，
本机无 CUDA）。

> `env.cmd` 里的注释**必须是纯 ASCII**：cmd.exe 按 ANSI 读 `.cmd`，UTF-8 中文注释会被解成乱码，
> 半行当成命令执行（2026-10-25 实际踩过）。

## 2. 摄像头识别指令（三种，按用途选）

### 2.1 实时预览（调机位、看框稳不稳）

```powershell
.\env.cmd scripts\camera_demo.py                      # 本机默认 index 1 / dshow
.\env.cmd scripts\camera_demo.py --camera-index 1 --backend dshow
```

> `camera_demo.py` 与 `camera_demo_dynamic.py` 的 argparse 默认值仍是旧的 `1 / msmf`，
> 与 `grasp_point.py`（`1 / dshow`）不一致——**以实际能出图的那个为准**，打不开就换后端。
> 预览窗口会独占相机，跑 `grasp_point.py` 之前必须先关掉它。

**必须注意**：`camera_demo.py` 会检查相机实际分辨率与 `config/calibration.json` 的
`image_size`（1280×720）是否一致，不一致直接退出并提示重标。这是**保护而非障碍**——
用错分辨率的单应矩阵会把坐标整体算偏。

### 2.2 单次出点（真正驱动机械臂用的）

```powershell
.\env.cmd scripts\grasp_point.py --frames 9          # 人读
.\env.cmd scripts\grasp_point.py --frames 9 --json   # 脚本读，stdout 只有一行 JSON
.\env.cmd scripts\grasp_point.py --frames 9 --trial 3 # 试验归档：points.jsonl + run03.png
```

输出 `x_mm / y_mm` 加一条可直接粘贴到板端的 `BOARD_CMD`。几个必须看的字段：

| 字段 | 含义 | 判读 |
| --- | --- | --- |
| `spread_mm` | 9 帧中心的极差 | >3 mm 说明框在跳，先稳光照/对焦 |
| `belt_iou` | 当前带面与 `calibration.json` 四边形的重合度 | <0.5 → 相机被碰过，标定失效，必须重标 |
| `conf_margin` | top1 与 top2 的置信度差 | <0.15 → 两个目标都像（夹爪被误检成 Cube），出的点不可信 |
| `inside_belt_quad` | 中心是否在标定带面内 | false → 极可能是误检 |

`--trial N` 会把每轮的 JSONL 与带框取证图自动落到 `vision_runs/closedloop_<日期>/`，
这是闭环成功率的原始证据，**别手工抄数**。

### 2.3 单图测试（换素材、写文档配图时用）

```powershell
.\env.cmd scripts\image_demo.py .\example.jpg --output .\out.jpg --device cpu
```

## 3. 从像素到运动的五跳（每一跳在哪、用什么）

```
① 相机取帧            640×480 或 1280×720 BGR      vision/camera.py
        ↓
② YOLO 检测           像素框 + 中心 (u,v) + 置信度   vision/detector.py → best.pt
        ↓
③ 平面单应            (u,v) → (x_mm, y_mm)          vision/plane_calibration.py
        ↓             原点=传送带左下角、+x 沿带长、+y 沿带宽
④ 示教表插值          (x_mm,y_mm) → ID1/ID2/ID3      scripts/grasp_point_map.py
        ↓             双线性反距离加权，<4 点退化为最近邻
⑤ 状态机下发          六轴目标 → PL 拼帧 → 舵机       scripts/g3_station_runner.py
```

**关键：第 ③ 跳和第 ④ 跳必须用同一套毫米坐标系。** 这是整条链路最容易错、且错了之后
"看起来像机械精度问题"的地方。

第 ⑤ 跳之后的一切都在 PL 里：帧由 PL 拼、限位由 PL 裁、六轴同步广播由 PL 调度、
到位判定由 PL 数"连续三轮进带"。PS 只负责"去哪"，PL 保证"怎么去、不出界、按时到"。

## 4. 怎么保证"像素点"和"运动指令"真的对得上

四层校验，**从便宜到贵**，出错时按顺序排查：

### 4.1 方向校验（30 秒，最容易做）

物块沿传送带往 +x 方向挪 10 cm，看 `grasp_point.py` 报的 `x_mm` 是不是**同向增大**。
再把物块往 +y 挪，看 `y_mm`。方向反了就是标定角点点反了（点了 原点→+y→对角→+x）。

### 4.2 姿态一致性校验（录点时就做）

`teach_add_point.py` 会比对当前 ID4-6 与 `grasp` 步的固定姿态，偏差 >30 就告警。
**姿态不一致的点插值出来没有意义**——ID1-3 换了、腕部朝向没换，末端位置就变了。

### 4.3 单调性校验（录完 3 点立刻做）

`x_mm` 递增时 ID1 应当**单调变化**，且变化方向与手工摆臂一致。若出现非单调，
说明某个点的 x 量错了（比如从带右端量的），必须重录。

### 4.4 闭环校验（真抓之后）

抓住后把物块放回原处，对比"视觉报的 (x,y)"与"实际抓到的位置"。偏差应
**小于物块半宽（约 10 mm）**。偏差大且方向一致 → 示教点系统性偏了；偏差随机 → 视觉抖动。

### 4.5 一条必须知道的系统误差：视差

标定平面是**传送带面**，物块有高度，所以物块**顶面**中心投影到带面坐标系时会偏。
偏差量级 ≈ 物块高度 × 相机倾角。相机越俯视，视差越小；越侧视，越大。

对策：**标定点时用物块的"抓取点"（夹爪包住时的位置）而不是顶面中心**，让这层误差
被示教表吸收掉。不要试图用公式修正——没有内参，修正不了。

## 6. 你（从 SD 卡录入开始）的完整步骤

```sh
# ① 挂载与拷包（PL 没动，不用重烧卡）
ls /run/media/
SD=/run/media/mmcblk0p1
mkdir -p ~/rtcs/scripts ~/rtcs/config
cp "$SD"/g3_station_runner.py "$SD"/g3_offline_plan.py "$SD"/grasp_point_map.py "$SD"/teach_add_point.py ~/rtcs/scripts/
cp "$SD"/g2_measured_limits.toml "$SD"/g3_station_plan.json "$SD"/g3_station_plan.template.json ~/rtcs/config/
cd ~/rtcs && ls scripts config          # 应有 4 个 py + 3 个配置

# ② 只读确认
sudo rtcs-pl-g2-six --uio /dev/uio0 limits      # ID2 max=2500、ID4 max=3100
sudo rtcs-pl-g2-six --uio /dev/uio0 diagnose    # 六轴 servo_error 全 0

# ③ 录三个示教点（臂摆到该点、夹爪包住物块、ID4-6 与 grasp 步一致）
sudo python3 scripts/teach_add_point.py --x-mm 60  --y-mm 40
sudo python3 scripts/teach_add_point.py --x-mm 240 --y-mm 40
sudo python3 scripts/teach_add_point.py --x-mm 420 --y-mm 40

# ④ 干跑，确认插值只改 ID1-3
sudo python3 scripts/g3_station_runner.py config/g3_station_plan.json --uio /dev/uio0 \
    --grasp-xy 240,40 --teaching-table config/grasp_teaching_table.json --once --dry-run

# ⑤ 真跑
sudo python3 scripts/g3_station_runner.py config/g3_station_plan.json --uio /dev/uio0 \
    --grasp-xy 240,40 --teaching-table config/grasp_teaching_table.json --once

# ⑥ 把表存回 SD（~/rtcs 是 RAM，断电即丢）
cp ~/rtcs/config/grasp_teaching_table.json "$SD"/ && sync
```

**PC 与板子之间的坐标怎么传**：今天用**人抄两个数**（`grasp_point.py` 已经把整条命令打印好）。
这是刻意的——先验证"坐标对了能抓中"，再谈自动化。网络传输（UDP 一行 JSON）等成功率稳定后加，
那时如果传错，你能立刻分辨是链路问题还是映射问题。

## 7. ROS2 以后需要吗

**不需要，而且现在引入是净损失。**

| 维度 | 判断 |
| --- | --- |
| 竞赛红线 | 要求"AI PC 出策略 + FPGA 实时控制"。ROS2 是中间件，**不产生任何指标**，评委不看 |
| 现有链路 | 已经是最短路径：PC 推理 → 传两个 float → 板端执行。ROS2 只是把这两个 float 包进话题 |
| 板端代价 | PetaLinux 装 ROS2 要拉大量依赖，initramfs 体积有限，且会引入新的启动失败面 |
| 工期 | 3 人、20 天。引入 ROS2 = 新增一层没人踩过的坑 |
| 答辩 | "为什么不用 ROS2"能答成工程权衡（实时性由 PL 保证、链路越短越可控），是**加分**答案 |

**什么时候才考虑**：如果决赛后要接"多机协同"或"板端直连相机"，那时再用。当前不碰。

> 参考：`Material_Library/kr260_robotic_arm-main/opencv_ros2/` 里有 ROS2 版本的颜色识别抓取，
> 可以借鉴其**流程划分**，但不要照搬框架。

## 8. 一句话总结这条链路

> 相机拍一张 → YOLO 给框 → 单应算成传送带毫米 → 示教表查成三个关节目标 →
> PS 下发六轴目标 → PL 拼帧、裁限位、同步广播、数到位 → 舵机抓。
>
> **PS 只说"去哪"，PL 保证"怎么去、不出界、按时到"。这就是 Zynq 在这个项目里的位置。**
