# 大模型协作记录

赛题要求（AMD 选题指南 3.3.3.1）提交"体现大模型协作过程的交互记录，含提示词、模型回答与自我
纠错轨迹"。本文件按**主题**整理协作过程，每条都对应仓库里可核验的代码、配置或证据文件。

> 说明：原始会话是中文对话，跨三人的开发机与 IDE，逐字记录量大且含路径等噪声。此处做结构化摘录：
> 保留**当时的提问意图、模型给出的方案、我们如何验证、错在哪里、最后怎么改**。
> 每条末尾的"落点"是指向仓库文件的锚点，评委可据此核对这条结论是否真的进了代码。

## 1. 反光导致白方块不可检（2026-10-14 ~ 10-15）

**提问**：绿色 PVC 皮带上放白色 40 mm 方块，YOLO 在桌面背景正常，上带后检不出；同时画面里出现
1474 个检测框，置信度 ≥0.5 的占大半但都不是方块。请给出排查顺序。

**模型回答（摘要）**：按"物理层 → 采集层 → 推理层"三步定位；先确认曝光与增益是否可编程，再判断
是镜面高光冒充目标还是真目标被过曝吞掉；建议先压曝光做对照实验，不要直接重训模型。

**验证**：`live_test` 加 `--auto-exposure/--exposure/--gain` 参数做扫参，exposure=-5 时侧拍工况稳定；
俯拍仍是 1474 个检测、conf≥0.5 只降 75% 不清零。

**纠错**：模型一开始倾向"数据不够、自训一版"。我们否掉了——信号特征是"高光区域被当成 cube"，
自训只会把这个错误特征学得更牢。改为治理光学：压曝光 → 调灯/角度 → 换 90° 无畸变镜头 + CPL 偏振片。
换相机后工况重置，旧标定与训练数据全部作废，重做标定。

**落点**：`docs/engineering-notes.md` §6 反光治理段（明确写"不要回退"）；
`vision_v11/…/config/calibration.json`（10-17 之后重标）。

## 2. 判据必须能证伪（2026-10-18 前后）

**提问**：七步状态机每步都返回 success，但实物经常没夹到。怎么让"假成功"进不了统计？

**模型回答（摘要）**：加一个与运动结果正交的观测量。舵机在夹住工件时会堵转，位置反馈停在接触位；
空夹会一路合到目标位。建议用闭爪后的位置差做判据，并给出阈值取法（取两类样本间距的一半以下）。

**验证**：夹住停在 2364–2409，夹空停在 2214–2216，差 170+ count，阈值取 60 count 有 2.8 倍余量；
后来又发现闭爪**耗时**同样能判（夹住 1010 ms 等满观测窗、夹空 562 ms 提前返回），且比读回位置早一整轮。

**纠错**：模型最初建议"用夹持力传感器"，被否——增加硬件会毁掉"不加传感器"这个卖点，且现场没有件。

**落点**：`scripts/static_grasp_server.py` 的 `grip=contact|empty` 判定；`metrics/README.md` 判据行。

## 3. 硬门禁把已经实测的位点挡住了（2026-10-19）

**提问**：想在脚本里加一条 `ID2 ≤ 2000` 的检查，"防止"错误位点把机械臂顶到底座。

**模型回答（摘要）**：可以加，但先问一句——这个 2000 是从哪来的？如果是几何推算而不是实测回读，
它就不是约束而是猜测；猜测写成硬门禁，会把正确的实测位点一起拦掉。建议先只告警。

**结果**：确实拦掉了。place 段的合法位点被这条启发式直接拒答，当天进度停摆。当天立规矩：

- 任何会阻止既定任务继续执行的检查，默认只能是告警，不得 `fail`/`exit`/拒绝执行；
- 位点数值只能来自现场 `diagnose` 实测，没实测就不填、不猜。

**落点**：`CLAUDE.md` "禁止自作聪明的硬门禁"整节；`README.md` 同步声明。

## 4. 动态抓取连踩四个坑（2026-10-29）

**提问**：`g5_dynamic_trigger.py` 发了 `dynamic_stage`，机械臂不动，日志只写 `grip=fault`。

**模型回答（摘要，四条按顺序给）**：
① 串口把发出去的字节回显回来，被我们当成板端回复——按 `{}` 提取而不是整行解析；
② 闭爪观测窗 `observe_ms=600` 低于板端下限，C 命令判参数错误、一帧都没发；
③ "是否越线"判断里先清标志再判断，永远判成"还没开始"；
④ 夹爪过载回包把整条六轴命令拖死，需要逐轴忽略掩码。

**纠错**：模型第一版只给了 ①，修完仍不动；我们把三段中间量（发出的字节、板端回包、PL fault 码）
全部打印出来，才定位到 ②③。教训写进工作方式：**不猜，先把中间量打印出来**。

**落点**：`scripts/g5_dynamic_trigger.py`；`docs/engineering-notes.md` §8 故障表最后三行。

## 5. 命中率 69% → 93.8%（2026-10-29 ~ 10-30）

**提问**：13 轮只中 9 轮，失败都是"爪过去了但工件没进开口"。方案层面该改什么？

**模型回答（摘要）**：三种改法——(a) 提前守在固定拦截点等；(b) 按预测时刻推进、到位即咬合；
(c) 缩短闭爪延迟。推荐 (b)+(c)，因为 (a) 的不确定性来自"工件要自己走过整个开口"。

**验证**：(a) 正是当时的做法，开口内行程约 57 mm；(b) 后缩短到约 23 mm。同时把闭爪从"上层脚本
串行调用 runner"（每次启动 880 ms，等于工件走 59 mm）改成直调板端单轴快路径。

**结果**：9/13（69%）→ 15/16（93.8%），单轮 7.28 s → 4.59 s。

**纠错**：模型一度建议"把带速当成常数、离线标定一次即可"——实测同一档位拟合值在 60–67 mm/s 之间跳，
固定值算提前量误差超过 20%。改为每轮用最近 12 帧最小二乘现估。

**落点**：`docs/engineering-notes.md` §5；`evidence/g5-dynamic-20261030.md` 逐轮数据。

## 6. 整机把速度顶到 1500 反而更慢（2026-11-03）

**提问**：把七步速度全部顶到 `SPEED_MAX_RAW=1500`，为什么反而出现"抓完不放置就复位"？

**模型回答（摘要）**：单轴行程大的段（ID2 可达 762 count）在高速下更容易撞进舵机低速死区或触发过载
保护，`place` 段的失败会被状态机当成"到位"继续往下走。建议只对短行程段提速，长行程段保持分级。

**验证与处理**：确实如此。速度退回分级值（standby/approach/grasp 1000、lift/place 1200、
retreat/exit 1400），调速只走 `scripts/set_plan_speed.py` 且一次只动一两步。

**落点**：`config/g3_station_plan.json`；`docs/engineering-notes.md` §4 末段。

## 7. 协作方式本身（可复用的部分）

| 做法 | 为什么有效 |
| --- | --- |
| 先让模型复述约束（板卡型号、ABI、限位是编译期常量、不许猜位点），再提问 | 约束写在提问里，能挡掉一半"通用方案" |
| 要求给"排查顺序"而不是"最终答案" | 现场问题多是多因叠加，顺序比结论值钱 |
| 每条建议必须能被一条命令验证 | 验不了的建议不采纳 |
| 把失败写进仓库（故障表、CLAUDE.md、notes） | 同一坑不踩第二次；也是本文件能写出来的原因 |
| 让模型读仓库文件而不是复述我们的描述 | 描述会漂，代码不会 |

这些做法已提炼为 `skill/` 下的两个技能包（`zynq-6dof-rtcs`、`rtcs-image-build`），
适用范围与失效条件见 `skill/README.md`。
