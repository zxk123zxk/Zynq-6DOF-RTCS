## 通读 rtcs_pl_g2.c / rtcs_pl_g2_six.c 全链路并评估风控门禁冗余

- 走通 ABI 0x5254000E 的完整链路：PS 用户态 CLI → UIO mmap（AXI4-Lite）→ axi_lite_regs.sv →（单轴）rtcs_top 内联 G2 状态机 /（六轴）g2_six_axis_controller + g2_descriptor_guard → hx30hm_g1_engine.sv 组帧 → uart_byte_tx 1 Mbps 8N1 → OBUFT 三态门 → 舵机总线。
- 确认线上帧与内部操作码的映射：OP1 PING、OP2 READ 0x38×2、OP11 READ 0x28×1、OP9 TORQUE_OFF(0x28<-0)、OP8 TORQUE_MOVE(0x28..0x2F 共 8 字节原子帧，长度 0x0B)、OP10 SYNC_TORQUE_MOVE(广播 ID 0xFE，长度 0x3A=58，62 字节)。
- 校验和规则：CS = ~(ID+LEN+INST+PARAM...) & 0xFF。
- 冗余评估结论（重要，供后续清理参考）：
  - 死代码：safety_monitor.sv 与 trajectory_engine.sv 从未被例化；servo_bus_master.sv 仅作并联 RX 观察器（tx/输出无消费者）。
  - 未被消费的寄存器：REG_CONTROL(0x04)、REG_COMMAND(0x08)、REG_PROFILE_SPEED(0x38)、REG_PROFILE_ACCEL(0x3c)、REG_DEADLINE_LO/HI(0x40/0x44)、REG_SERVO_CONFIG(0x48)、REG_G2_START(0x114 恒 0)——G0 轨迹引擎遗留。
  - 重复校验：PS 侧限位/速度预检与 PL 提交校验读同一组编译期常量；g2_descriptor_guard 的 inhibit 与 deadline 检查与 g2_six_axis_controller 自身预检重复（guard 独有的是限位 + 标定掩码）。
  - 疑似过窄门禁：release 仅允许 ID 1；calibrate-step 仅允许 ID 2..6（排除 ID 1），而 move 允许 1..6，三者不一致。
  - 建议保留：G1 白名单 fault 13、PL 提交校验、guard 的限位/标定检查、物理 estop_n。

## 追加：ID 5 运动故障归因修复（PL + CLI）

操作者现象：`--id 5 --target 2000` 成功（2322→2014，fault=0）；`--target 1000`（起点 1931）与
`--target 3000`（起点 2012）均 `write_sent=1 unicast_ack=0 fault=8`，无任何 sample。

关键发现：
- 根因看不出来**不是**因为舵机，而是因为 `rtcs_top.sv` 的 `G2_WRITE_WAIT` 把**任何**引擎故障
  （3 超时 / 4 长度 / 5 停止位 / 6 应答ID / 7 校验和 / 8 舵机ERROR）都写成 `g2_fault_code <= 8`。
  所以 CLI 打印的 `fault=8` 不能推出“舵机报错”。归档 `docs/2...md` 表里那条
  `G1_FAULT=8 / G1_RESULT=0x00100000` 才证明那一次确实是舵机 ERROR=0x10。
- 查 HX-30HM V3.7 官方表（docs/resource_file/HX-30HM寄存器列表及参数.xls）：
  0x41 bit4 = 角度；0x2A 目标位置范围 -30719..30719；0x2E 运行速度 0..3400 步/s；
  0x29 加速度 0..254；0x13 保护控制初值 44（bit2/3/5 温度/电流/过载开，bit4 角度关）；
  0x21 运行模式默认 0=位置伺服；**0x2C 是“PWM开环速度”（仅模式2有效），不是“运行时间”**
  ——工程把 `--time-raw` 写进 0x2C，位置模式下被舵机忽略；表里**没有**角度限位寄存器，
  所以“角度错误”是动态错误（位置超差/堵转），不是静态越界拒绝。

已改（ABI 保持 0x5254000e，纯增量、只读）：
- `rtcs_pkg.sv`: 新增 `REG_G2_DIAG = 9'h118`（[23:16] ERROR、[15:8] 阶段、[7:4] 轴、[3:0] 引擎故障码）。
- `axi_lite_regs.sv`: 新增输入 `g2_diag` 与新读分支。
- `rtcs_top.sv`: 单轴 G2 在提交/发送/反馈三处锁存 `g2_diag_*`；写应答失败时同时
  `g2_last_servo_error <= g1_servo_error`。
- `hx30hm_g1_engine.sv`: **TURN 期间冲刷 uart_byte_rx**（半双工自收：校验和恰为 0xFF 时
  会被当成应答帧头，报出虚假的应答ID不符/校验和故障）。`tb_rtcs_g2_one_servo` 仍通过。
- `rtcs_servo_diag.h`: 新增 `engine_fault_name()` / `engine_fault_class()`（transport vs servo_error）。
- `rtcs_pl_g2.c`: 优先读 G2_DIAG 锁存，缺失时回退 G1_FAULT/G1_RESULT（0D 板端也能用）；
  告警式接受 ABI 0D；ERR 行给出 engine_class/engine_reason + HINT。
- `rtcs_pl_g2_six.c`: 同款 ABI 0D 兼容 + engine_class/engine_reason + diagnose 的 read_fault_reason。
- `sim/tb_axi_lite_regs.sv`: 补 `.g2_diag` 连接。
- `sim/run_pl_g2_cli_guard.sh`: 新增锁存路径用例（G2_DIAG 与 G1_FAULT 故意冲突，
  断言 CLI 采用锁存快照）。

验证：`bash sim/run_regression_wsl.sh` → `RTCS_WSL_REGRESSION_PASS`（WSL Verilator 5.008）；
三个 CLI 守护脚本单独复跑均通过。CLI 另经 `-std=c11 -Wall -Wextra -Werror` 语法检查。
**注意：RTL 改动需重综合 bitstream 才生效；CLI 改动需重建 petalinux 应用包。留存的
ID 5 “角度错误”根因（舵机侧负载/位置超差）仍需用 0x3C/0x45/0x42 遥测复测确认。**

| **0x1F 位置校正** | **0** | **`79 08`** | bit11=1 → **−121 步** |
| 0x00 固件版本 | 3.7 | **3.15** | XLS 描述的是 3.7 |
| 0x28 扭矩开关 | — | 0（卸力） | 断电后 SRAM 复位 |

**最值得盯的假设：`position_offset = −121` 决定可用窗口。** 数值巧合很扎眼：
`2048 − 121 = 1927`，而实测能到达的最低位置就是 **1930**；窗口半宽实测 ~100 与 |−121| 同量级。
→ 假设窗口 ≈ **[1927, 2169] = 2048 ± 121**。
**锐利的可证伪预测：`--target 2100` 应成功、`--target 2200` 应失败。**
反证注意：伺服曾在 2322 被读到（若那是命令到达的而非手推的，窗口就比 2169 宽）。

**下一步只需要一条数据：ID 1 / ID 3 的 dump 做对照**（同总线，无需改接线）。

## 追加：三轴对照 dump 到手 —— ±121 窗口假设被证伪，但机理被钉死

对照结果（ID 1 / ID 3 / ID 5，各 22 条，`probes=22 ok=22 failed=0`）：**除 `0x1F 位置校正` 与
`0x38 当前位置` 外，逐字节完全相同。** 0x1F 依次为 ID1 `FD 01`(+509)、ID3 `ED 0A`(−749)、
ID5 `79 08`(−121)，按 XLS「bit11 为方向位」解读。0x38 为 1999 / 2883 / 1930（当前位置，天然不同）。
负载、电流、电压、温度、保护掩码、PID、过流阈值、运行模式、固件版本全部一致。

**证伪 1：`0x1F` 不能解释窄窗口。** ID5 的 `−121` 预测窗口 ≈[1927, 2169]，但实测
`--target 2100` 与 `--target 2200` **都报 `fault=8 / servo_error_raw=0x10 / write_sent=1 / phase=write_ack`**。
更本质的反驳：0x1F 的取值范围 ±2047 步，只能把零点整体搬移或给出 ≥4094 宽的区间，
在算术上**无法产生 <±100 的绝对窗口**。所以机制不在 0x1F。

**由 ID 5 全部尝试记录推出的机理（与上述寄存器无关，纯行为归纳）：**
| 事实 | 数据 |
| --- | --- |
| 唯一被接受的目标 | **只有 2000**；1000/1500/1600/1700/1800/1900/2100/2200/2500/3000 全被拒 |
| 行程大小无关 | 2322→2000（Δ=−322）**成功**，1989→1900（Δ=−89）**失败** |
| 离当前距离无关 | 距当前 322 步成功，距当前 89 步失败 |
| 方向无关 | −322 成功、−89 失败；+57 成功、+100(2100) 失败 |
| 原始速度/时间无关 | speed 500 与 1500、time_raw 0/10/100/200 两侧都出现 |
| 拒绝时刻 | `elapsed_ms=5`，舵机尚未开始动；状态包 ERROR=bit4 |
→ **舵机持有的是一个「绝对目标窗口」，中心≈2000–2048，半宽明显小于 100 步**（1900 与 2100 都在外）。
这不是行程限制、不是电流/负载问题、不是游隙，也不是我们任何一行代码能产生的（RTL/CLI 中
对舵机 NVS 地址 0x1F/0x13/0x37 无任何写路径，已 grep 确认）。

**关键缺口：V3.7 寄存器表从 0x08 直接跳到 0x0D、从 0x1C 跳到 0x1F。**
Feetech 系固件恰好把「最小/最大角度限制」两个 16 位字段放在 0x09–0x0C，而"目标越界即报角度错误"
正是待验证的机制。本轮已把它补成实测项。

## 追加：Vivado 构建被阻断的真正原因（环境结论，长期有效）

## 追加：ID 5 根因定位完成 —— 舵机 0x09/0x0B 角度限制是窄窗口

操作者板端跑 `sweep` 对照 ID 5 / ID 1。**72 个地址中只有 7 个不同**（`0x05` ID 本身、
`0x09`、`0x0B`，以及随姿态变化的 `0x38/0x43/0x45/0x3F` 位置/电流/温度）；**其余 65 个逐字节相同**。
操作者初判"两者无区别"，实际两个功能差异恰好落在 **V3.7 表跳过的空档 0x08..0x0D** 内：

| 舵机 | 0x09 | 0x0B | 反解出的 16 位窗口 |
| --- | --- | --- | --- |
| ID 5 | `86` | `01` | **min=1926、max=2049 → [1926, 2049]** |
| ID 1 | `E9` | `FB` | min=1001、max=3067（与实测 [1000,3000] 吻合） |

反解唯一性：目标 2000 被接受 ⇒ min≤2000≤max；1900 被拒 ⇒ min>1900；2100/2200 被拒 ⇒ max<2100。
低字节 `0x86` 候选里只有 1926 满足前两条；`0x01` 候选里只有 2049 满足后两条。
**该窗口与全部实地记录逐条吻合（含起点 2322→2000 成功、位移 322 步）。**

**决定成败的是舵机内部绝对位置允许窗口，由 0x09/0x0B 这对角度限制持有。ID 5 这对被改成
围绕 2000 的极窄区间；ID 1 是正常大范围，所以能走 1000..3000。**

**与我们哪个 ABI 无关**：`hx30hm_g1_engine.sv` 在 `rx_index==4` 处取 ERR 字节
（`servo_error <= rx_byte`），WRITE 的 `fault=8` 就是舵机自己回的 `0x10`。
⇒ **重综合 bitstream 不可能让 ID 5 接受 2100**，舵机在 WRITE 应答里就拒了。

**新的工具伪影（重要，已写进 docs/2）：** 该舵机不忠实回答所有单字节 READ —— 单独读 16 位
字段的高字节会返回固定 `0xD0`（单字节读 0x11 → D0，而 2 字节读 0x10 → [E8 03]）。
涉及地址 `0x0A 0x0C 0x11 0x19 0x20 0x2B 0x2D 0x2F 0x31 0x39 0x3B 0x3D 0x44 0x46`；
另有别名伪影：单字节读 0x43 与 0x38 返回同一值，而 0x38 多字节读给出真实位置。
⇒ **`sweep` 已改为偶地址双字节读取**（`words=36 bytes=72 ok=36 failed=0 read_only=1`），
16 位字段一律以多字节读取为准；上述 14 个 0xD0 不得写入任何结论。

**确认命令（当前镜像的 `dump` 已含 4 字节读 `gap_09_0c`，无需重刷）：**
`sudo rtcs-buslinker-g1 --device /dev/ttyACM0 --id 5 dump`
预期 `raw=[86 07 01 08]`（即 0x0786 / 0x0801）。修复需用幻尔官方软件写回 0x09/0x0B；
**不得为写寄存器而放宽 BusLinker 的只读约束**（回归逐帧断言只发 READ）。

**本轮改动：** `sweep` 改双字节对齐块（消除自身伪影）、修正 `bytes=` 计数、更新守护脚本与
docs/2；新增对照报告 `artifacts/reports/sweep-id5-id1-20261010.txt`；
回归 `RTCS_WSL_REGRESSION_PASS`；镜像重建 `artifacts/sd/`（`BOOT.BIN` 未变，PL 未重综合）。
**未跑 Vivado**：操作者的授权附了"若比特流是原因"的前提，而证据表明不是，故先回报。
